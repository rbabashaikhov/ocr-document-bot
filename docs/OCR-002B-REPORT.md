## Фактические наблюдения о структуре

### Блоки, абзацы и порядок

`blocks[]` и `lines[]` содержат достаточно данных, чтобы не терять переносы строк в исходных блоках. Однако порядок массива нельзя принимать за глобальный порядок чтения: в `table.png` после блока с минимальной координатой `y=111` следующий блок имеет `y=62`; в `mixed.png` после левой колонки с `y=326` появляются блоки правой колонки с `y=195`. В OCR-003 чтение должно опираться на геометрию (кластеризация по строкам/колонкам и `boundingBox`), а не только на индекс блока.

Семантическая классификация полезна, но неполна: text-сценарий состоит только из `LAYOUT_TYPE_TEXT`, а mixed-сценарий выделил section headers. Следовательно, `layoutType` следует сохранять как сигнал, но нельзя автоматически считать все абзацы или уровни заголовков восстановленными без правил renderer-а.

### Таблицы и объединения

Для `mixed.png` Vision вернул таблицу с `rowCount=6`, `columnCount=2`; все 12 адресов ячеек заполнены, у каждой есть геометрия, и все фактические `rowSpan`/`columnSpan` равны 1. Этого достаточно для семантической DOCX-таблицы без объединений.

Критический отрицательный результат: на `table.png`, который визуально содержит сложную шапку и объединения, Vision с моделью `page` не вернул `tables[]` вовсе. Поэтому на основании реальных данных OCR-002B нельзя считать API достаточным для гарантированного восстановления настоящих DOCX-таблиц с объединёнными ячейками. Доступные поля `rowSpan`/`columnSpan` документированы, но в этом прогоне не были получены в реальном ответе. Нельзя строить fallback-таблицу из порядка текстовых блоков без отдельной геометрической эвристики и измерения её качества.

### Markdown и качество

`markdown` появился только в проверке с моделью `markdown`, что согласуется с документацией. Его нужно рассматривать как альтернативное семантическое представление, а не как доказательство сохранения исходной геометрии: текстовый и table-сценарии `page` не вернули Markdown. Официальная схема указывает `pictures[].score` как confidence расположения картинки; наши ответы не содержали картинок и не дали документированного confidence текста. Следовательно, авто-решения по качеству OCR пока не имеют достоверного числового входа.

## Команды трёх сценариев

Команды ниже зафиксированы для воспроизводимости. Не запускайте их повторно без нового согласования: три разрешённых платных распознавания уже выполнены. Каждая сохраняет полный неизменённый JSON локально; файлы игнорируются Git.

```bash
# 1. Абзацы: page model — проверка blocks, lines, layoutType и порядка чтения.
uv run python -m ocr_document_bot.cli local-testdata/ocr-002b-text.png \
  --model page \
  --output fixtures/vision/ocr-002b-text.json \
  --allow-billed-request

# 2. Простая таблица: page model — проверка tables, cells, индексов и span.
uv run python -m ocr_document_bot.cli local-testdata/ocr-002b-table.png \
  --model page \
  --output fixtures/vision/ocr-002b-table.json \
  --allow-billed-request

# 3. Смешанный документ: markdown model — сопоставление markdown с blocks/tables.
uv run python -m ocr_document_bot.cli local-testdata/ocr-002b-mixed.png \
  --model markdown \
  --output fixtures/vision/ocr-002b-mixed.json \
  --allow-billed-request
```

У API ограничение в 10 MB на файл и 20 Мп на изображение; для синхронного метода PDF должен быть одностраничным. [Официальные квоты и лимиты](https://yandex.cloud/en/docs/overview/concepts/quotas-limits), [синхронный REST API](https://aistudio.yandex.ru/en/docs/vision/ocr/api-ref/TextRecognition/recognize).

## План анализа после разрешённого прогона

Для каждого захвата исследованы и обезличенно описаны:

1. `textAnnotation.blocks[]`: порядок массива, `layoutType`, блоки/линии и соответствие абзацам/заголовкам.
2. `tables[]`: количество строк/столбцов, полный набор `cells[]`, `rowIndex`, `columnIndex`, `rowSpan`, `columnSpan`, текст ячейки и geometry.
3. `boundingBox.vertices`: согласованность координат блоков, таблиц и ячеек с ожидаемым порядком на странице.
4. `markdown`: наличие только при выбранной модели, различия с полями структуры и отсутствие изображений в Markdown.
5. Показатели качества: только документированные `pictures[].score`; схема не подтверждает confidence для текста, строк, блоков или ячеек.

### Критерий достаточности для DOCX-таблицы

Ответ считается достаточным для семантической таблицы, если `rowCount`, `columnCount` и все ячейки позволяют построить непересекающуюся сетку, а `rowSpan`/`columnSpan` корректно описывают объединения. В анализе будут отдельно отмечены отсутствующие ячейки, выход за границы, пересечения и расхождение визуального порядка с индексами. Даже при достаточной структуре OCR-003 должен определить правила форматирования, ширины колонок и заголовков; renderer в OCR-002B не создаётся.

## Рекомендации для OCR-003

1. Проектировать `DocumentModel` так, чтобы сохранять raw `blocks`, line breaks, `layoutType`, bbox и полноценные таблицы/cell spans, но различать «структура распознана» и «текст геометрически расположен».
2. Для таблиц использовать два режима: прямое восстановление только при наличии непротиворечивых `tables[]`; отдельный явно маркированный fallback по геометрии для таблиц без `tables[]`. Не выдавать fallback за точное восстановление.
3. До DOCX renderer-а согласовать тестовый набор с известными ground truth, содержащий merged cells, и измерять: table detection, заполненность сетки, точность spans и порядок чтения. Потребуется новое разрешение на дополнительные OCR-вызовы.
4. Не использовать `markdown` как единственный источник DOCX: сочетать его с `tables[]`, `blocks[]` и bbox. Не включать raw fixtures либо исходные документы в Git.

OCR-003 не начинается в рамках OCR-002B; Document Model, DOCX renderer, Telegram и Email не реализовывались.

# OCR-004C — исследование восстановления сложных таблиц

## Границы этапа

Проверен только локальный прототип `research/table_grid.py`. Он не импортируется OCR Engine, Yandex mapper или DOCX Renderer и не меняет их поведение. Для опыта добавлен `opencv-python-headless` в группу dev-зависимостей. Новых запросов в Yandex Vision не выполнялось.

Исходные изображение, OCR JSON и результаты находятся только локально: `tests/samples/`, `fixtures/vision/` и `artifacts/ocr-004c/` исключены из Git. В отчёте не приводятся конфиденциальные фрагменты документа.

## Метод

1. Изображение переводится в grayscale и бинаризуется Otsu.
2. Морфологическое открытие длинными горизонтальным и вертикальным ядрами отделяет правила таблицы от текста.
3. Группы соседних пикселей в проекциях дают координаты рядов и колонок.
4. Кандидат принимается только при не менее чем трёх линиях каждого направления и достаточно непрерывной внешней прямоугольной рамке (минимум 75% покрытия каждой стороны). Это важная защита от текста, подчёркиваний и элементов страницы.
5. Пересечения соседних линий образуют минимальные ячейки. Если участок внутренней границы отсутствует, соседние минимальные ячейки объединяются; объединение сохраняется лишь если его область прямоугольная.
6. OCR-блок относится к одной ячейке по центру `boundingBox`; для результата фиксируются индексы сопоставленных и несопоставленных блоков. Поэтому проверяются потеря и дублирование текста.

Порог непрерывности и размеры ядер выводятся из размера изображения, а не из фиксированных координат тестового файла. Прототип намеренно не пытается угадать таблицу без визуальных правил.

## Результат: сложная таблица OCR-002B

В `tests/samples/table.png` обнаружена замкнутая сетка:

| Показатель | Результат |
| --- | --- |
| Горизонтальные границы | 6 |
| Вертикальные границы | 9 |
| Базовая сетка | 5 строк × 8 столбцов (40 минимальных слотов) |
| Итоговых прямоугольных ячеек | 29 |
| OCR-блоков | 21 |
| Сопоставлено | 21, без повторов |
| Не сопоставлено | 0 |

Отсутствующие сегменты внутренних правил дали наблюдаемые `row_span` и `column_span`: в частности, верхняя часть сетки содержит горизонтальное объединение, а ряд заголовков — вертикальные объединения. Пустые ячейки сохранены как ячейки без блоков. Overlay с синей/красной базовой сеткой, зелёными границами итоговых ячеек и точками OCR-блоков сохранён в `artifacts/ocr-004c/complex-table/grid-overlay.png`; машиночитаемый результат — рядом в `grid-analysis.json`.

Это подтверждает, что для данного документа есть достаточно пиксельных свидетельств для восстановления редактируемой сетки. Это не является доказательством корректности смыслового содержания: OCR-текст принимается как полученный Vision и не исправляется.

## Защита от ложных срабатываний

На реальном `tests/samples/text.jpg`, где нет видимой табличной рамки, первоначальные проекции могли образовать ложные линии. После обязательной проверки четырёх сторон внешнего прямоугольника результат — `no ruled table detected`; артефакт находится в `artifacts/ocr-004c/no-border-text/`. Synthetic-тест также проверяет, что обычная строка текста не становится таблицей.

Такой фильтр делает подход сознательно консервативным: он откажется от таблицы с оборванной внешней рамкой, вместо того чтобы изготовить ложную структуру.

## Ограничения и ошибки, которые ещё возможны

- Метод работает только при достаточно контрастных, почти осевых видимых правилах. Перспектива, поворот, толстые/пунктирные линии, шум скана и частично обрезанная рамка требуют предварительного deskew/line-repair.
- Отсутствие сегмента линии — геометрическое свидетельство объединения, но не абсолютное: сегмент может быть потерян качеством изображения. Поэтому результат должен иметь уровень уверенности и не должен автоматически заменять исходные блоки при слабом сигнале.
- Распределение блока по центру не решает блок, который действительно пересекает две ячейки, и не восстанавливает форматирование внутри ячейки.
- Нельзя применять этот подход к таблицам без видимых границ: отсутствие рамки должно оставлять данные абзацами или `table_candidate`, а не создавать таблицу.
- Прототип не исследует линии внутри растровых картинок и не выполняет OCR повторно.

## Рекомендация

**Доработать перед интеграцией, а не переносить прототип напрямую.** Для OCR-004C показана жизнеспособность CV-подхода на сложной таблице с явной сеткой и объединениями. Следующий исследовательский шаг должен добавить deskew, оценку уверенности каждого ребра/объединения, набор разнородных анонимизированных примеров и ручное сравнение с эталонными сетками. В production pipeline следует принимать результат только при сильной замкнутой рамке, достаточной плотности пересечений и однозначном сопоставлении блоков; иначе сохранять текущие Paragraph/`table_candidate` без потери текста.
